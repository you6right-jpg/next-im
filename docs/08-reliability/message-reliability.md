# 消息可靠性设计

## 1. 三种确认状态

| 状态 | 含义 | 确认方 |
|---|---|---|
| Server Accepted | 服务端已持久化接受 | 服务端 |
| Delivered | 接收端 SDK 已收到并按约定持久化 | 接收端 SDK |
| Read | 用户已读 | 接收端业务 / SDK |

WebSocket 写成功不等于 Delivered；推送成功也不等于 Delivered。

## 2. 发送端幂等

- 创建消息时生成 `client_msg_id`。
- 同一条消息重试必须复用该 ID。
- 服务端唯一约束 `(app_id, sender_id, client_msg_id)`。
- 重复请求返回原消息 ID 和 seq，不重复创建消息。

## 3. 服务端事务

建议在一个事务中：
1. 校验租户、用户、会话和发送权限。
2. 检查 client_msg_id 幂等。
3. 原子分配会话 seq。
4. 写入消息。
5. 写入 Outbox 事件。
6. 提交事务。
7. 返回 Server Accepted ACK。

## 4. Outbox 分发

Outbox Worker 扫描未投递事件，投递 Kafka 或内部事件总线。投递成功后更新状态。消费者必须幂等，因为至少一次投递可能重复。

## 5. 接收端处理

1. 收到消息。
2. 按 message_id 或 conversation_id + seq 去重。
3. 本地事务持久化。
4. 更新同步游标。
5. 发送 Delivered ACK。

若 ACK 丢失，服务端可重发；SDK 必须安全去重。

## 6. 离线同步

- 每个会话维护服务端 seq。
- 客户端保存每会话同步游标。
- 重连后按游标拉取缺失数据。
- 实时推送与增量同步可重叠，客户端去重。
- 游标失效时支持重新建立基线或全量分页同步。
- 撤回、成员变更等影响客户端状态的事件也必须可同步。

## 7. 必须测试的故障

- 服务端持久化成功但 ACK 丢失。
- 客户端发送后断网。
- 接收端落库后 ACK 丢失。
- Worker 重复消费。
- Kafka 暂时不可用。
- WS 节点重启。
- 用户多设备同时在线。
- 客户端本地数据库迁移失败。
