# 数据库分库分表与索引策略

## 1. 设计原则

在 IM 系统的初期，我们采用单库（或主从复制）的架构以降低复杂度并快速迭代。但随着业务发展，消息、连接等高频数据表的数据量会急剧增长。因此，我们必须在设计之初就为未来的分库分表（Sharding）做好准备，遵循以下原则：

- **隔离性**：所有的业务数据都必须包含 `tenant_id` 和 `app_id`，以支持 SaaS 模式下的租户隔离和数据分片。
- **Sharding Key 明确**：在核心大表的设计中，必须明确定义 Sharding Key。查询时尽量带上 Sharding Key，避免跨库/跨表扫描。
- **平滑迁移**：分库分表策略必须支持不停机的平滑扩容，采用双写或增量同步结合全量校验的方案。

## 2. 核心表的分片策略

### 2.1 消息表 (`im_message` / `im_message_user_state`)
消息数据是 IM 系统中增长最快的数据。
- **Sharding Key**：`conversation_id`。因为消息总是基于会话进行查询和同步的，将会话内的消息路由到同一个分片可以避免跨片查询。
- **分表策略**：
  - 早期：按时间（如按月分表）或者 Hash(conversation_id) 进行分表。
  - 远期：根据 `tenant_id` 进行分库（大租户独占库），库内再根据 `conversation_id` Hash 分表。
- **注意**：如果单聊和群聊的会话 ID 格式不同，需要确保它们的 Hash 规则一致。

### 2.2 用户与关系表 (`im_user`, `im_friend`, `im_group_member`)
- **Sharding Key**：`user_id`（对于用户和好友关系表）；`group_id`（对于群成员表）。
- **分库分表**：根据 `tenant_id` + `app_id` 进行分库，库内按 `user_id` 或 `group_id` 进行 Hash 分表。

### 2.3 离线同步游标表 (`im_user_sync`)
- **Sharding Key**：`user_id`。
- **策略**：因为同步请求总是由特定用户/设备发起的，按 `user_id` 分片可以保证单用户的同步请求落到同一节点。

## 3. 索引设计规范

- **主键索引**：推荐使用分布式发号器（如 Snowflake 算法或其变种）生成全局唯一的趋势递增 ID，避免使用数据库自增 ID，以利于后续的分表。
- **联合索引**：
  - 任何针对租户数据的查询，必须将 `app_id` (或 `tenant_id`) 作为联合索引的最左前缀。
  - 示例：对于 `im_message`，索引设计为 `(app_id, conversation_id, seq)`，以满足会话内消息按 `seq` 同步的需求。
- **唯一索引约束**：
  - 发送端幂等：`(app_id, sender_id, client_msg_id)` 必须唯一。
  - 服务端序列：`(app_id, conversation_id, seq)` 必须唯一。
- **避免大表上的低选择性索引**：例如单纯的状态字段（如 `status`），不要单独建索引。

## 4. 冷热数据分离与归档

- **冷热分离**：消息表应支持按时间归档。比如超过 6 个月的历史消息可以迁移到归档表或归档库，甚至导入到对象存储 / 列式存储中。
- **查询降级**：客户端请求远古历史消息时，服务端应明确区分从热库还是冷库查询，并适当限制查询频率和时间跨度。
